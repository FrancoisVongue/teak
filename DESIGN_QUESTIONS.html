growable_region — регион, который растёт

крит-путь склонение есть, но есть и подвопрос

Примитив: регион, чей блок памяти может вырасти, когда заполнился — без инвалидации уже выданных Handle.

Проверил по коду: хендл — это {slot, offset, len, expected_gen}, доступ резолвится косвенно через слот (ORTO_SLOTS[slot].base + offset), а не сырым указателем. Значит при росте через realloc достаточно обновить базу в слоте — все живые хендлы остаются валидными даром. Это четвёртый источник блока рядом с region/stack_region/aligned_region, тот же тип Region, та же работа. Разблокирует реальные сервера и unbounded-сценарии (парсер строит дерево неизвестного размера, vec растёт).

A. Четвёртый конструктор, прозрачный ростсклоняюсь
// тот же тип Region, тот же ref/r[i]/len.
// growable_region(start) растёт x2 на ref,
// когда текущий блок заполнен.
arena g = growable_region(4096);

let mut i = 0;
while i < 100000 {
    let _ = ref(g, i);   // даже если блок полон —
    i := i + 1;          // realloc, база в слоте обновлена,
}                        // старые хендлы валидны.
let h = ref(g, 42);
g[0]                     // работает как обычно
  • Ортогонально: ноль новых user-facing понятий, четвёртый источник блока.
  • Косвенность хендла уже есть → реализация дёшева (~50 строк runtime + AST-узел).
  • Та же gen/bounds-проверка, тот же синтаксис доступа.
  • Амортизированный ref: изредка O(n) копия при realloc (стандартная цена роста).
B. Отдельный тип Growable + явный grow
arena g = growable_region(4096);
// рост — отдельная операция, не на ref:
grow(g, 8192);          // пользователь сам решает когда
let h = ref(g, 42);
  • Рост виден явно в точке вызова.
  • Новое понятие/тип рядом с Region — НЕ ортогонально, дублирует ось.
  • Перекладывает «когда расти» на пользователя — это и есть та грязь, которую прячут в примитив.
  • Два типа региона = каждая функция, берущая Region, теперь думает «а какой».
C. Не добавлять — цепочка регионов
// пользователь сам пере-аллоцирует:
arena r1 = region(4096);
// заполнился — заводит новый, копирует:
arena r2 = region(8192);
// ... и тащит это руками
  • Ноль изменений компилятора.
  • Боль уезжает в каждый call-site → ровно анти-N+M.
  • Хендлы из r1 не переносятся в r2 автоматически — ручная миграция, источник багов.
  • Делает невозможными «сервер без заранее известного размера» элегантно.
Подвопрос, который реально надо решить тебе (и он не про синтаксис): as_ptr(handle) отдаёт сырой текущий адрес. Его используют для FFI — например uring_read(r, fd, as_ptr(buf), len(buf), ...) передаёт буфер ядру. Если регион вырастет (realloc) пока ядро пишет в этот буфер (in-flight async read через await), буфер уедет → ядро пишет в освобождённую память. Тихий use-after-free, мимо gen-проверки (сырой указатель её не проходит).

Варианты ответа: (i) growable только для построения структур, а I/O-буферы держим в обычном region — соглашение/документация; (ii) запретить рост, пока есть «pinned» хендлы, отданные через as_ptr (нужен учёт — сложно); (iii) рост только между await-точками (рантайм-инвариант одноядерного шедулера — возможно само собой выходит). Я склоняюсь к A + правило (i) как стартовая честная позиция: growable — для «строю дерево/вектор», I/O-буфер — фиксированный регион. Но это твой звонок, потому что он трогает модель безопасности.

#1

? для Result/Option — проброс ошибки

вкусовой, лёгкое склонение

Примитив: пробросить «плохую» ветку finite-outcome значения вверх без ручного match, ранним возвратом.

Напряжение с законом явности (#2): ранний возврат частично скрыт. Но он виден в точке ? — это не ambient catch. Работает только если охватывающая функция возвращает совместимый Result/Option; типы это форсят. Go намеренно не имеет ? (пишут if err != nil) — это многословно; ? — это Messi-слой поверх явной модели.

A. Без ? — явный match (как сейчас)сейчас
fn load(r: Region) -> Result[Config] {
    let raw = match read_file(r) {
        Ok(b)  => b,
        Err(e) => { return Err(e); }
    };
    let cfg = match parse(r, raw) {
        Ok(c)  => c,
        Err(e) => { return Err(e); }
    };
    Ok(cfg)
}
  • Полностью явно, ноль сахара, ноль вопросов.
  • Каждый исход обработан на месте — taste §2 в чистом виде.
  • Реальная повторяемость: один и тот же match-проброс копируется (taste §13 — повод абстрагировать).
  • Длинные цепочки I/O тонут в церемонии — ровно «как Go, но больно».
B. Постфиксный ?склоняюсь
fn load(r: Region) -> Result[Config] {
    let raw = read_file(r)?;   // Err -> return Err(e)
    let cfg = parse(r, raw)?;  // Ok(v) -> v
    Ok(cfg)
}
// `?` desugar строго в тот match из колонки A.
// Виден в коде. Тип load обязан быть Result.
  • Убирает ровно ту повторяемость, что в A — и ничего больше.
  • Не ambient: ? виден глазом, тип функции форсит совместимость.
  • Чисто живёт с регионами: ранний возврат идёт вверх по стеку, регион ещё жив.
  • Маленькая «магия»: поток управления в точке ? неявен на 1 шаг.
C. Префиксный try-блок
fn load(r: Region) -> Result[Config] {
    try {
        let raw = read_file(r);
        let cfg = parse(r, raw);
        Ok(cfg)
    }
    // любой Err внутри блока -> ранний выход
}
  • Группирует «зону проброса» явным блоком.
  • Сильнее скрывает: какие именно вызовы могут выйти — не видно построчно.
  • Ближе к exception-семантике, которую мы отвергаем (ambient-ish).
  • Новый управляющий конструкт vs точечный оператор.
Моё склонение — B, мягко. Аргумент: ? не прячет исход (тип остаётся Result, исчерпывающность сохраняется на границе), он убирает повтор проброса — это taste §13, а не нарушение §2. Он виден в точке. Это honest Messi-слой: убери его — система не перестраивается. Но это вкусовой звонок про «сколько шага неявности мы терпим» — поэтому без жёсткой подсветки. Если скажешь «нет, явный match — якорь», принимаю A без спора.

#2

Ambient-регион / box / in r

склонение ясное — упирается в уже принятый якорь

Примитив: как аллокация получает свой регион — явным параметром или из окружающего контекста.

Прямо на законе явности. Важно: вы уже отвергли «implicit allocator / alloc fn» с формулировкой «видимость аллокации (r-параметр) — якорь философии orto». Ambient-регион — это тот же отвергнутый примитив под другим именем.

A. Полностью явно (как сейчас)склоняюсь
fn build(r: Region) -> Handle[Tree] {
    let l = ref(r, Leaf);
    let n = ref(r, Node(20, l));
    n
}
// регион виден в сигнатуре И в каждой аллокации.
  • Где аллокация — видно глазом, всегда. Якорь философии держится.
  • Функция, берущая Region ⇒ она аллоцирует. Сигнатура не врёт.
  • Многословно: r протаскивается через всё дерево вызовов.
B. Ambient in r { } + box
fn build() -> Handle[Tree] {
    in r {
        let l = box(Leaf);       // в текущий r
        let n = box(Node(20,l)); // r не назван
        n
    }
}
  • Меньше шума: r не повторяется на каждой строке.
  • box(v) не показывает, КУДА аллоцирует — надо сканировать вверх до in r. Это та самая «невидимая магия».
  • Это уже отвергнутый implicit-allocator под именем ambient.
  • Thread-local «текущий регион» плохо живёт с кросс-ядром (#8).
C. Соглашение «Handle в возврате сигналит»
// НЕ фича, а правило чтения:
// возвращает Handle[T] ⇒ обязан брать Region.
fn build(r: Region) -> Handle[Tree] { ... }
// без региона Handle вернуть нельзя —
// компилятор и так это форсит.
  • Ноль новой машинерии — это просто чтение существующих сигнатур.
  • Сохраняет полную явность из A.
  • Не уменьшает многословность — это лишь лоск документации, не решение «шума».
Склоняюсь к A, и это редкий случай, где подсвечиваю уверенно: ambient (B) — это буквально implicit allocator, который вы уже отвергли как противоречащий якорю. C — не фича, а просто верное наблюдение про чтение сигнатур (его можно записать в стиль-гайд бесплатно). Многословность r реальна, но цена честная и совпадает с «жертвуем скоростью компиляции/многословностью, не семантикой». Если многословность правда болит на практике — это аргумент за #1 (?) и #3 (inout), а не за скрытие региона.

#3

inout-параметры

чистый сахар, низкий приоритет

Примитив: функция меняет значение вызывающего без алиасинга и без сырых указателей.

Чистый desugar в «верни новое значение + перепривяжи». Никакого скрытого алиасинга. Для copyable-типов. С линейными не дружит (copy-in копирует — запрещено), так что inout только для нелинейных.

A. Возврат + перепривязка (как сейчас)сейчас
fn bump(c: Counter) -> Counter {
    Counter { n: c.n + 1 }
}
let mut c = Counter { n: 0 };
c := bump(c);     // явная перепривязка
c := bump(c);
  • Полностью явно: видно, что c пере-присвоен.
  • Ноль новой семантики.
  • Шум x := f(x) повторяется; для многополевых out — возврат кортежа.
B. inout (copy-in / copy-out)
fn bump(inout c: Counter) {
    c.n := c.n + 1;
}
let mut c = Counter { n: 0 };
bump(c);          // desugar: c := bump_ret(c)
bump(c);          // ноль алиасинга, value-семантика
  • Убирает x := f(x)-шум, особенно для out-параметров.
  • Honest desugar — это та же модель, просто короче. Нет указателей/алиасинга.
  • Маленькая неявность: мутация у вызывающего не видна как присваивание на call-site.
  • Не работает с линейными — ещё одно «нельзя для этого вида» (но оно следует из закона копируемости, не спец-правило).
Склоняюсь отложить, оставить A. inout — приятный Messi-сахар, но чистый: его можно добавить в любой момент позже без перестройки, потому что это буквально desugar в то, что уже есть. Сейчас он не на крит-пути и не разблокирует ничего. Добавим, если протаскивание out-значений реально заболит в stdlib/HTTP. Не трачу на него решение сейчас, если ты не видишь иначе.

Generic Option/Result над linear-типами

есть чистый прецедент → склонение

Примитив: завернуть линейный ресурс (Fd, Socket) в Option/Result, не теряя линейности.

Сейчас Option[Fd] запрещён (Fd линеен, Option — нет). Workaround: возвращать сырой int и fd_wrap вручную — некрасиво. Но: вы уже делаете ровно это для Handle[linear] — компилятор сам генерит каскадный drop. Вопрос: распространить тот же закон на агрегаты.

A. Запрет (как сейчас)сейчас
// Option[Fd] нельзя. Возвращаем сырьё:
fn try_open(p: Handle[byte]) -> int {
    open_raw(p)        // -1 при ошибке
}
let raw = try_open(path);
let r = if raw >= 0 {
    // вручную оборачиваем в линейный Fd
    use_fd(fd_wrap(raw))
} else { handle_err() };
  • Ноль работы в системе типов.
  • Сырой int + ручной wrap — обходит линейность ровно там, где она нужна.
  • «-1 как ошибка» — это lying-category (taste §6): int прикидывается и fd, и ошибкой.
B. Linear-aware: агрегат над linear ⇒ linearсклоняюсь
// закон: агрегат, содержащий linear-поле,
// сам линеен, и компилятор ГЕНЕРИТ его drop —
// match по вариантам, drop каждого linear-поля.
fn try_open(p: Handle[byte]) -> Option[Fd] {
    let raw = open_raw(p);
    if raw >= 0 { Some(fd_wrap(raw)) } else { None }
}
match try_open(path) {
    Some(fd) => use_fd(fd),   // fd потреблён
    None     => handle_err(),
}   // drop_Option[Fd] сгенерён: Some -> drop(fd)
  • Тот же механизм, что уже есть для Handle[linear] — это обобщение закона, не новое спец-правило (taste §13, закон-природы #3).
  • Убирает lying-category «-1»: исход назван (None/Some(Fd)).
  • Компилятор знает структуру Option/Result ⇒ генерит drop без всякого typeclass.
  • Нужно решить охват: только встроенные Option/Result, или ЛЮБОЙ enum/struct с linear-полем.
Склоняюсь к B, потому что у него есть чистый прецедент: вы уже генерите каскадный drop для Handle[linear]. «Агрегат над linear сам линеен, drop генерится из структуры» — это та самая природа-закон, из которой и Handle[linear], и Option[Fd] следуют автоматически, а не два спец-случая.

Настоящий вопрос для тебя — охват: делаем это только для встроенных Option/Result (тогда чуть пахнет спец-случаем) или формулируем общий закон «любой агрегат с линейным полем → линейный агрегат с генерированным каскадным drop» (тогда он заодно поглощает Handle[linear] и нынешний запрет «linear в data-position обычной структуры» становится не запретом, а «структура становится линейной»)? Второе — глубже и ортогональнее, но это уже не мелочь: меняет правило про linear-в-структурах. Твой звонок, какой охват берём.

#5

Variadic format

AK-47 сейчас / Messi потом

Примитив: собрать строку из шаблона и разнородных типизированных аргументов.

Болит на практике (netlink/debug). Ловушка: «настоящий» runtime-variadic с разнородными типами требует диспатча «render по типу аргумента» — а это typeclass, который мы отвергаем. Поэтому развилка не «variadic да/нет», а «как рендерить разнородное без классов типов».

A. Без variadic — concat-цепочки (как сейчас)сейчас
let msg = concat_all(r, ref(r, [
    str_of(r, "x="),
    int_to_bytes(r, x),
    str_of(r, " y="),
    int_to_bytes(r, y),
]));
  • Работает сегодня, ноль новой машинерии.
  • Каждое преобразование явно и типизировано.
  • Многословно и шумно — болит ровно как сказано.
B. Builder-цепочка (stdlib, без variadic)сейчас
let msg = fmt(r)
    .s("x=").i(x)
    .s(" y=").i(y)
    .done();
// каждый метод типизирован: .i(int), .s(str),
// .f(float). Поведение впрыснуто per-use,
// никакого диспатча по типу.
  • AK-47: чистая stdlib, ноль изменений компилятора (закон «простой компилятор»).
  • Полностью явно и total — нет lying-category, каждый .i/.s/.f знает свой тип.
  • Это orto-способ: поведение как значение, поздно, per-use.
  • Чуть длиннее идеального format("x={} y={}", x, y).
C. Comptime-format (раскрытие на этапе компиляции)Messi, потом
// типы аргументов известны на call-site ⇒
// компилятор парсит строку и РАСКРЫВАЕТ:
let msg = format(r, "x={} y={}", x, y);
//  -> concat_all(r, [int_to_bytes(x),
//                     int_to_bytes(y)])
// для своих типов — передать render явно.
  • Самый эргономичный, выглядит как Zig comptime.
  • Без runtime-variadic и без typeclass: чистый compile-time desugar по известным типам.
  • Требует comptime-парсинга формат-строки в компиляторе — реальная сложность против закона «~4k строк».
  • Для пользовательских типов всё равно нужна явная render-функция (впрыск) — иначе скрытый класс типов.
Склоняюсь: B сейчас, C — кандидат на потом. Builder (B) даёт 90% эргономики ценой нуля строк компилятора и идеально ложится на «поведение впрыском, поздно, per-use» из вашей же доктрины дженериков. Comptime-format (C) красивее на вид, но покупает это сложностью в компиляторе и всё равно упирается в «render пользовательского типа» — там опять явный впрыск. Поэтому: строим B как stdlib (это вообще один из параллельных агентов), а C держим как опциональный Messi, если {}-синтаксис реально захочется. Если хочешь сразу целиться в C — скажи, это меняет, кого из агентов запускать.

#6

Nested patterns в match

guards уже есть → отложить

Примитив: сопоставлять вложенные конструкторы/литералы: Some(0), Node(0, Leaf).

Сейчас Some(x) биндит x, но литерал на месте (Some(0)) не матчится. Guards в arm’ах уже есть и закрывают ~80%. Полный nested — «big refactor» emit’а. Это вопрос бюджета сложности компилятора, не философии.

A. Только guards (как сейчас)сейчас
match o {
    Some(x) if x == 0 => zero_case(),
    Some(x)           => nonzero(x),
    None              => empty(),
}
  • Уже работает. Ноль работы.
  • Покрывает большинство реальных кейсов.
  • Чуть многословнее, чем Some(0) =>; глубокая вложенность неудобна.
B. Литералы во вложении
match o {
    Some(0) => zero_case(),
    Some(x) => nonzero(x),
    None    => empty(),
}
  • Чище для частого «совпасть с конкретным значением».
  • Требует goto-based fallthrough в ADT-switch emit — заметная работа.
  • Маржинальный выигрыш над guards, которые уже есть.
C. Полный nested
match t {
    Node(0, Leaf) => ...,
    Node(v, kids) => ...,
    Leaf          => ...,
}
  • Самый выразительный, классический паттерн-матчинг.
  • Самый дорогой по компилятору (рекурсивная декомпозиция + полнота).
  • Против закона «простой компилятор» при текущем приоритете.
Склоняюсь отложить (A). Guards уже закрывают 80%, а B/C — это бюджет сложности компилятора, который сейчас лучше потратить на крит-путь (growable + HTTP). Ваш же закон: «никаких фич ради фич — каждая ось закрывает реальную боль из практики». Вернёмся, когда практика HTTP/stdlib покажет, что guards правда жмут. Если у тебя уже есть конкретная боль — назови, пересмотрю.

Escape-анализ и судьба stack_region

направление задано философией, открыта реализация

Примитив: молча класть не-убегающий регион/env на стек; убрать user-facing stack_region как ярус.

Это прямо ваш якорный пример: «ноль-стоимость должен давать escape-анализ как оптимизация, а не @escaping-ярус как в Swift». Значит конечное состояние философией уже выбрано — стек выбирается доказательством, молча. Открыто не «делать ли», а как: точность анализа и что с stack_region в переходный период.

A. Оставить stack_region явным (как сейчас)сейчас
arena stk = stack_region(1024);  // пользователь
arena hp  = region(4096);        // выбирает ярус
  • Работает, предсказуемо.
  • Это user-facing ярус «быстрый/удобный вариант одного и того же» — ровно та грязь Swift, которую вы критикуете.
  • Пользователь должен знать про escape вручную — утечка внутренней заботы наружу.
B. Молчаливый escape-анализ (конечная цель)направление
arena r = region(4096);   // ОДИН способ.
// компилятор доказал, что r не убегает
// из scope -> разместил на стеке молча.
// stack_region исчезает как понятие.
  • Ортогонально: один способ для пользователя, перформанс прячется в оптимизацию (якорь).
  • Убирает user-facing ярус — снимает грязь.
  • Реальный статический анализ: точность vs консервативность, цепляет замыкания и возврат Handle. Серьёзная работа.
  • Нельзя выкидывать stack_region, пока анализ не построен — иначе регресс без замены.
C. Гибрид: анализ молчит + stack_region как override
arena r = region(4096);          // анализ решает
arena s = stack_region(1024);    // ручной форс,
                                 // если анализ консервативен
  • Безопасный переходный режим: анализ строится, override остаётся как страховка.
  • Если оставить override навсегда — это снова ярус, грязь возвращается.
  • Хорош как стадия: C сейчас → B когда анализ созреет.
Это не «выбери колонку», а roadmap-пункт. Конечная цель — B (она следует из вашего якоря, тут сомнений нет). Открытое и глубокое — сам анализ: где провести границу точность/консервативность, как обращаться с замыканиями (env в регионе) и с функциями, возвращающими Handle (это и есть escape). И тактический звонок: идём через переходный C (анализ молчит, stack_region временно остаётся override и выпиливается, когда анализ докажет, что не нужен), или строим B сразу и держим stack_region до самого включения. Я бы шёл через C как стадию, с явной целью схлопнуть в B. Но это большая работа не на крит-пути — вопрос приоритета: когда.

#8

Кросс-ядерная конкурентность

самое глубокое — не подсвечиваю

Примитив: исполнять на нескольких ядрах (thread-per-core), не нарушив модель «регион — один владелец, память не пересекает ядро».

seastar-уровня. При thread-per-core аллокатор по-ядерный ⇒ владение памятью не пересекает ядро. Тут я реально не подсвечиваю — это открытый дизайн, где можно ошибиться, и его надо думать вместе. Ниже — четыре подвопроса, каждый с пространством решений. Рисую геометрию, формулирую вопрос; ответы — за тобой/совместно.

8a. Память между ядрами

i. Shared-nothing + копия
// данные на ядро B = глубокая копия,
// отправленная по каналу. Владелец-регион
// никогда не пересекает границу.
  • Простейшая модель владения: ничего не шарится, ноль гонок.
  • Идеально для мелких сообщений.
  • Дорого для крупных данных (копия по объёму).
ii. Process-global shared-аллокатор + free-back
// крупные буферы — в общем аллокаторе;
// ядро B читает, по завершении шлёт
// free-back-сообщение ядру-владельцу A.
  • Без копий крупных данных.
  • Второй аллокатор рядом с регионом — новая ось памяти (риск против N+M).
  • free-back-протокол = ручная дисциплина времени жизни через ядра.
iii. Seastar-шард: передача владения
// регион/буфер мигрирует на ядро B
// (move владения), A больше не трогает.
// нужен «Send»-вывод (см. 8d).
  • Без копий, единая модель владения (move, как линейность).
  • Ложится на уже существующую линейность.
  • Per-core аллокатор: освобождать на чужом ядре нельзя — нужен free-back или возврат владения.

8b. Распределение соединений

i. SO_REUSEPORT, accept на каждом ядре
// каждое ядро держит свой listen-сокет,
// ядро & соединение совпадают, данные
// не пересекают границу.
  • Соединение живёт целиком на одном ядре — нет пересечения границы.
  • Линейно масштабируется, ядро шарит nothing.
  • Балансировка на усмотрение ядра (хэш), возможен перекос.
ii. Один accept + handoff
// одно ядро принимает, раздаёт fd
// другим ядрам -> снова пересечение
// границы (fd + начальное состояние).
  • Точная балансировка нагрузки.
  • Handoff = пересечение границы на каждое соединение (ровно то, чего избегаем).
  • Accept-ядро — потенциальное горлышко.

8c. Каналы и backpressure

i. SPSC на пару ядер
// по одному lock-free кольцу на
// направление пары ядер. N*(N-1) колец.
  • Простейший lock-free, максимально быстрый.
  • N² колец при росте числа ядер.
ii. MPSC на ядро-приёмник
// одно кольцо на ядро-приёмник,
// много отправителей.
  • N колец вместо N², проще топология.
  • Contention на стороне отправителей.
backpressure / select
// общий вопрос для обоих: что когда
// кольцо полно (блок/дроп/await),
// и нужен ли select по нескольким.
  • Нужно решить семантику «полно»: await на месте ложится на async-модель.
  • select по нескольким источникам — отдельная конструкция.

8d. «Send»-ность — что можно пересылать через ядро

i. Структурный вывод (без аннотаций)
// тип «Send», если внутри нет
// локального Handle/Region этого ядра.
// Выводится из структуры, не объявляется.
  • Ноль аннотаций — ложится на «без классов типов», выводится сам.
  • В духе orto: свойство — тень структуры, не объявление способности.
  • Точное правило — открыто (что именно делает тип не-Send: только локальные хендлы? сырые указатели? linear-ресурсы конкретного ядра?).
ii. Явный маркер (как Rust Send)
// тип объявляет Send-способность.
  • Явно и предсказуемо.
  • Пахнет классом типов / способностью — против вашей доктрины (вид, не способность).
  • Ручная аннотация там, где структура и так всё знает.
Не подсвечиваю — это тот самый глубокий узел, где надо думать вместе и можно ошибиться. Что я вижу как тяготение (но не утверждаю): 8a-iii + 8b-i + 8d-i образуют связную геометрию — «соединение целиком на одном ядре (shared-nothing), владение мигрирует move’ом только когда надо, Send выводится структурно как тень линейности». Это переиспользует уже имеющуюся линейность вместо новой оси. Но: per-core аллокатор + free-back (8a) — реально нерешённая часть, и она тащит за собой 8c. Это единственный вопрос, который я бы предложил не закрывать на бумаге сейчас, а вынести в отдельную глубокую сессию — он не на крит-пути к первому числу (одноядерный HTTP его не требует) и заслуживает того же уровня разбора, что и память/линейность. Твой звонок: думаем сейчас или паркуем до после первого бенча.

Type-level alignment

мелочь → оставить как есть

Примитив: кодировать выравнивание региона в типе vs рантайм-аргументом.

Сейчас alignment — рантайм-keyword: aligned_region(N, A). Альтернатива — затащить его в тип (Region[Page]). Маленький вопрос, привожу для полноты.

A. Рантайм-аргумент (как сейчас)сейчас
arena aln = aligned_region(4096, 4096);
// один тип Region, выравнивание — параметр.
  • Один тип Region — функции не плодят варианты по выравниванию.
  • Просто, явно, уже работает.
  • Выравнивание не отражено в типе (нельзя статически требовать page-aligned).
B. Type-level Region[Page]
fn dma(r: Region[Page]) -> ... { ... }
// тип гарантирует выравнивание статически.
  • Статическая гарантия выравнивания на границе функции.
  • Расщепляет Region на семейство типов — против «один тип Region, один способ».
  • Сложность системы типов ради редкого кейса (DMA/mmap).
Склоняюсь оставить A. Region[Page] расщепляет единый Region на семейство ради статической гарантии, нужной в узких кейсах (DMA/GPU/mmap) — цена «один тип, один способ» выше выигрыша. Рантайм-keyword честен и прост. Пересмотрим, только если статическое требование выравнивания реально заболит. Низкий приоритет.
