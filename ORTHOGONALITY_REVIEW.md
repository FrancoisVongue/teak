# orto — обзор ортогональности после Stage 3

Этот документ — честный взгляд на то, что мы добавили в Stage 3, и где
это ломает наши собственные правила (см. `CLAUDE.md`):

> Каждая новая возможность должна стоить компилятору ровно столько,
> сколько занимает сама фича. Если приходится менять десять
> существующих мест, что-то идёт не так.

> Мы предпочитаем ортогональные оси: данные / управление /
> полиморфизм / память / FFI — каждая развивается независимо.

> Мы избегаем «каталога специальных правил». Правильная абстракция
> порождает поведение во всех конкретных случаях автоматически.

Stage 3 добавил большую новую ось — конкурентность. Ниже — перечень
вещей, которые получились или хорошо, или плохо.

---

## 1. Что вышло ортогонально

### 1.1. Linearity propagation в Task / Stream / Array

`Array[T]` где T линейный → массив сам линейный. `Task[Region]` →
линейный таск. `(Region, int)` → линейный кортеж. **Одно правило**:
«встроенные контейнеры наследуют линейность параметра».

Это закон, не каталог. Когда мы добавляли tuples, нам ничего не
пришлось делать с linear-проверками — они уже работали.

✅ Закон, не правило.

### 1.2. Single suspension point — `await`

`await` — единственное слово, помечающее приостановку. `yield` это
синтаксический сахар для `await nop()`. `for x in stream` это loop
выражение, но **каждая итерация** это implicit `await`.

Программист помнит одно слово.

✅ Минимальная поверхность.

### 1.3. `Result[T]` обёртка для `await`

`await op()` возвращает `Result[T]`. Положительный CQE → `Ok(T)`,
отрицательный → `Err(int)`. Компилятор форсит `match` (или
destructuring let через `Ok(x) = await ...`).

Это не магия — это нормальный ADT. `Result` это
`enum Result[T] { Ok(T), Err(int) }`. Просто привилегированный по
имени.

✅ Хороший fit с существующей системой типов.

### 1.4. State machine — невидимая трансформация

Async функция лоwers в `Frame_X` struct + `X_step()` + sync wrapper.
Программист этого не видит — пишет линейный код. Компилятор делает
работу.

✅ Поверхность не раздута.

## 2. Что вышло неортогонально — нужно обсудить

### 2.1. `Result` и `Option` как привилегированные builtins

**Что**: компилятор «знает» про `Result` и `Option`, инжектит их в
каждую программу, запрещает пользователю их объявлять.

**Проблема**: это два параллельных каталога:
- `Option[T] { Some(T), None }`
- `Result[T] { Ok(T), Err(int) }`

Если завтра захочется `Either[A, B]` или другую обёртку — нужен будет
третий привилегированный тип. Каталог растёт.

**Варианты решения**:

A) **Оставить как есть**. Дёшево, понятно, два хорошо известных типа.
   Третий вряд ли потребуется.

B) **Унифицировать через builtin `enum Optional[T, E]`** — заменяет
   и Option (E = unit) и Result (E = int). Усложняет API ради
   небольшой экономии.

C) **Поднять Option/Result в обычный stdlib** — снять привилегию.
   Тогда компилятор не должен «знать» про них. Но `await` тогда
   возвращает что? Нужен какой-то механизм связать stdlib type с
   compiler-generated lowering. Это делает stdlib частью language
   spec — не лучше builtin.

**Моё мнение**: A. Привилегия двух типов это минимальный налог. Не
ломаю.

### 2.2. `Task[T]` и `Stream[T]` — параллельные линейные типы

**Что**: два builtin linear типа с почти одинаковой реализацией —
оба слот в pool'е, оба резюмируются через CQE. `Task` один-разовый,
`Stream` multishot.

**Проблема**: дублирование. И drop'ы (`drop_Task` vs `drop_Stream`)
имеют разную семантику (detach vs cancel-TODO).

**Варианты**:

A) **Оставить как есть** — два хорошо различимых концепта в API.
   Программист видит «таск» или «поток» сразу.

B) **Унифицировать в `Future[T, Multishot]`** где Multishot — фантомный
   параметр или enum. Меньше дублирования, но shape для пользователя
   менее очевидна.

C) **`Task[T]` это `Stream[T]` остановившийся после одного события** —
   философски правда, но в коде вряд ли поможет.

**Моё мнение**: A. Дешевле два типа чем универсальный с дискриминатором.

### 2.3. `await all { ... }` — два режима одного синтаксиса

**Что**:

```orto
let (a, b, c) = await all { e1, e2, e3 };  // статика → tuple
let arr = await all task_array;            // динамика → Array[Result]
```

Один и тот же `await all`, два разных типа результата, два разных
лоwering'а.

**Проблема**: парсер выбирает по look-ahead (если `{` — статика, если
выражение — динамика). Это особое правило. Контекстная грамматика.

**Варианты**:

A) **Разные имена**: `await all { ... }` (статика) vs `await each
   coll` (динамика). Слова разные → шейпы разные. Но `each`
   некрасиво в этой позиции.

B) **Только один**: убрать статическую форму, оставить только
   динамическую (`await all <Array[Task[T]]>`). Программист сам кладёт
   таски в массив. Минус: heterogeneous types больше нельзя — массив
   гомогенный.

C) **Оставить как есть** — два режима, парсер дизамбигирует по `{`.

**Моё мнение**: B наиболее красивая, но теряем heterogeneous. C — то
что есть. Если выбирать — **C**, потому что heterogeneous static
полезна (например, parallel чтение разных файлов разной формы).

### 2.4. `yield` как отдельное слово

**Что**: `yield` — синтаксический ключевик. Семантически это `await`
на nop SQE.

**Проблема**: лишнее слово. Если есть `await`, `yield` это его частный
случай. По закону природы, не каталог: `await nop()` это уже yield.

**Варианты**:

A) **Убрать `yield`** — программист пишет `let _ = await orto_nop();`
   или похожее. Минус: каждая программа тащит nop extern. Плюс:
   меньше синтаксиса.

B) **Оставить как есть** — `yield` это сахар, маленький бонус
   эргономики. Net cost ~5 строк парсера.

**Моё мнение**: B. Один синтаксический сахар стоит дешевле, чем
загружать каждую программу импортом `nop`. Не ломаю.

### 2.5. `t.0` — числовое поле кортежа

**Что**: для кортежа `t` имеем `t.0`, `t.1`, ... Это не имя поля,
а индекс.

**Проблема**: оператор `.` имеет два разных значения — field-by-name
(struct) и field-by-index (tuple). Перегрузка.

**Варианты**:

A) **Оставить как есть** — Rust/Swift/Scala делают так же. Привычно.

B) **Только destructuring** — убрать `t.0`, оставить только
   `let (a, b, c) = t;`. Минус: нельзя читать одно поле без
   destructure'а.

C) **Индексирование `t[0]`** — но это конфликтует с Array index.
   Можно разводить по типу (tuple vs Array), но это снова контекстная
   логика.

**Моё мнение**: A. Распространённая практика, не ломаю.

### 2.6. `extern fn ... -> Task[T]` vs `extern fn ... -> T`

**Что** (после сегодняшнего cleanup'а): тип возврата extern'а
определяет calling convention. Task[T] / Stream[T] → SQE-prep,
скрытый аргумент `void *user_data`. Просто T → обычный sync FFI.

**Это хорошо ортогонально** — тип говорит правду, без модификаторов.

✅ Cleanup сделан в фазе 9.

### 2.7. Two flavours of drop function

**Что**: у нас есть **три** разных способа дропнуть линейное значение:

1. `drop_Region` — встроен в runtime.
2. `drop_<UserType>` — пишет пользователь для своего `linear struct`.
3. `drop_Array_<T>` / `drop_Tuple_<T0_T1>` / `drop_Task_<T>` /
   `drop_Stream_<T>` — генерируется компилятором per
   instantiation для induced linearity.

**Проблема**: три источника одной операции. Каталог.

**Варианты**:

A) **Оставить как есть** — каждый имеет своё место и происхождение,
   путаницы нет. Тёплое чувство «закон» при том что три механизма.

B) **Унифицировать через generated_drop fn table** — все drop'ы
   единый интерфейс. Но это runtime cost (vtable вызов) и сейчас
   они все статически разрешаются compiler'ом.

**Моё мнение**: A. Они *разные* по природе:
   - Region — встроенный примитив рантайма.
   - User linear — пользовательский resource cleanup.
   - Induced — структурный обход.

   Унификация скрыла бы это различие, не упростив.

### 2.8. `long long` ограничение на `Task[T]`

**Что**: результат таска передаётся через slot.result типа
`long long` (8 байт). Это ломается для T > 8 байт (например
`Task[Array[byte]]` — Array это 16-байтовый handle).

**Проблема**: специальное ограничение, не выражено в системе типов.
Программа компилируется, но результат повреждается.

**Это реальный bug, не косметика.**

**Варианты**:

A) **Расширить slot.result до union с inline buffer** —
   `union { long long ll; uint8_t bytes[32]; }`. Покрывает Array
   и большинство user structs. Стоит ~32 байта на slot.

B) **Использовать frame's return_value (T-типизированный) напрямую**
   — копировать через memcpy с known size T per instantiation.
   Уже частично сделано через `assign_to_blob` / `read_from_blob` —
   но slot.result ещё `long long`.

C) **Запретить Task[T]` для T размером > 8 байт** в check.ml. Не
   делает то что хочется, но честно.

**Моё мнение**: B. Расширить slot.result до достаточного буфера
(`uint64_t result[2]` = 16 байт покрывает Array). Это нужно сделать
честно. Можно сейчас починить.

Это **bug** — починю ниже.

### 2.9. `for i in lo..hi` vs `for x in stream`

**Что**: один `for` keyword, две разные семантики, парсер
дизамбигирует по `..`.

**Проблема**: контекстная грамматика. Программист видит `for ... in
...` и должен понять что это за цикл.

**Варианты**:

A) **Оставить как есть** — Rust/Python/Go делают так же. Привычно.

B) **`for i = lo to hi` для range, `for x in stream`** — два слова
   для двух случаев. Но `to` это лишнее keyword.

**Моё мнение**: A. Это распространённый case в индустрии, не ломаю.

### 2.10. `await all` reserves `all` как контекстное слово

**Что**: `all` — обычный идентификатор кроме как сразу после `await`.

**Проблема**: контекстная грамматика. Slight magic.

**Это допустимо** потому что:
1. `all` после `await` встречается строго в одной позиции.
2. Пользователь может назвать переменную `all` в любом другом месте.

✅ Tolerable.

### 2.11. Frame-binder `fr->` префикс — implementation detail

**Что**: внутри `async_rewrite_to_frame` мы переименовываем имена
переменных, добавляя `fr->` префикс. Это видно в `emit.ml` и
определяет emission shape.

**Это не language surface** — пользователь этого не видит. Но это
fragile implementation: detection через string-prefix matching.

**Варианты**:

A) **Оставить как есть** — работает, документировано.

B) **Завести отдельный AST-узел `TEFrameVar` / `TEFrameLet`** для
   frame-resident bindings. Чище, но добавляет 2 узла в AST и обходы
   в каждом проходе.

**Моё мнение**: A для V1. Если ещё кто-то ещё посмотрит на это место
и тоже скажет «странно», тогда B. Сейчас работает.

### 2.12. spawn-only-on-call ограничение

**Что**: `spawn worker(args)` — допустимо только когда внутри
вызов функции. `spawn 42` — отвергается с понятным сообщением.

**Проблема**: специальное ограничение.

**Это семантическая необходимость** — spawn нуждается в `f` и `args`
чтобы вызвать. Без вызова spawn не имеет смысла. Программа не может
скомпилироваться с любым другим shape.

✅ Не баг, а constraint of the construct.

## 3. Чек по N+M, не N²

Сколько мест компилятора задело Stage 3:
- ✏️ `token.ml` / `lexer.ml` — 4 keywords (`await`/`spawn`/`yield` ещё
  пара была удалена сегодня).
- ✏️ `ast.ml` — 5 новых узлов (EAwait, EAwaitAll[2 формы], ESpawn,
  EYield, EForStream), плюс tuples (3 узла).
- ✏️ `parser.ml` — соответствующая парсинговая логика.
- ✏️ `check.ml` — типизация (Task, Stream, Result, tuples,
  induced linearity propagation).
- ✏️ `mono.ml` — пробрасывание новых типов.
- ✏️ `emit.ml` — самый большой кусок: state machine, slot pool,
  runtime header, drop generators.

Это **много** — около 1500 LOC OCaml. Но это **одна ось** —
конкурентность. Если бы мы добавляли её несколько раз с разных углов
(один pass на await, другой на spawn, третий на Stream), было бы N².

По факту мы делали последовательно: каждая фаза опиралась на
предыдущую, **не модифицируя**. spawn использовал slot pool, который
тоже использовал await. Tuples использовали induced linearity которая
уже работала. И т.д.

Это **N+M**. Дорого, но честно.
