# orto — обзор ортогональности после Stage 3

Этот документ — честный взгляд на то, что мы добавили в Stage 3, и где
это ломает наши собственные правила (см. `CLAUDE.md`):

> Каждая новая возможность должна стоить компилятору ровно столько,
> сколько занимает сама фича. Если приходится менять десять
> существующих мест, что-то идёт не так.

> Мы предпочитаем ортогональные оси: данные / управление /
> полиморфизм / память / FFI — каждая развивается независимо.

> Мы избегаем «каталога специальных правил». Правильная абстракция
> порождает поведение во всех конкретных случаях автоматически.

Stage 3 добавил большую новую ось — конкурентность. Ниже — перечень
вещей, которые получились или хорошо, или плохо, и **решения** по
каждому пункту.

---

## 1. Что вышло ортогонально

### 1.1. Linearity propagation в Task / Stream / Array / Tuple

`Array[T]` где T линейный → массив сам линейный. `Task[Region]` →
линейный таск. `(Region, int)` → линейный кортеж. **Одно правило**:
«встроенные контейнеры наследуют линейность параметра».

Это закон, не каталог. Когда мы добавляли tuples, нам ничего не
пришлось делать с linear-проверками — они уже работали.

✅ Закон, не правило.

### 1.2. Single suspension marker — `await`

`await` — единственное слово, помечающее приостановку. `yield` это
синтаксический сахар для `await nop()`. `for x in stream` это loop
выражение, но **каждая итерация** это implicit `await`.

Программист помнит одно слово.

✅ Минимальная поверхность.

### 1.3. `Result[T]` обёртка для `await`

`await op()` возвращает `Result[T]`. Положительный CQE → `Ok(T)`,
отрицательный → `Err(int)`. Компилятор форсит `match` (или
destructuring let через `Ok(x) = await ...`).

Это не магия — это нормальный ADT. `Result` это
`enum Result[T] { Ok(T), Err(int) }`. Просто привилегированный по
имени.

✅ Хороший fit с существующей системой типов.

### 1.4. State machine — невидимая трансформация

Async функция лоwers в `Frame_X` struct + `X_step()` + sync wrapper.
Программист этого не видит — пишет линейный код. Компилятор делает
работу.

✅ Поверхность не раздута.

## 2. Спорные точки — решения

### 2.1. `Result` и `Option` как привилегированные builtins

**Что**: компилятор «знает» про `Result` и `Option`, инжектит их в
каждую программу, запрещает пользователю их объявлять.

**Проблема**: два параллельных каталога:
- `Option[T] { Some(T), None }`
- `Result[T] { Ok(T), Err(int) }`

Если завтра захочется `Either[A, B]` — нужен будет третий
привилегированный тип. Каталог растёт.

**Решение: оставить как есть.**

Эти два типа фундаментальны: Option это «может не быть значения»,
Result это «может быть ошибка». Третий, четвёртый аналогичный тип в
языковом ядре практически невозможен — все известные мне «опциональные
обёртки» сводятся к этим двум. Привилегия двух типов — фиксированный
налог в две строки регистрации (`builtin_option_decl`,
`builtin_result_decl`), не растущий каталог.

Если потребуется `Either[A, B]` — пользователь объявит его как
обычный `enum Either[A, B] { Left(A), Right(B) }`. Это работает.

---

### 2.2. `Task[T]` и `Stream[T]` — параллельные линейные типы

**Что**: два builtin linear типа с почти одинаковой реализацией —
оба слот в pool'е, оба резюмируются через CQE. `Task` один-разовый,
`Stream` multishot.

**Проблема**: дублирование.

**Решение: оставить как есть.**

Эти два типа отражают **две принципиально разные семантики
завершения**:
- Task: один CQE — один результат. `await task` забирает его.
- Stream: много CQE — много результатов. `for x in stream` дренирует.

Унификация в `Future[T, Multishot]` с фантомным параметром скрыла бы
это различие в типе и тем самым в чтении кода. Это потеря, не
выигрыш. Два простых типа дешевле универсального с дискриминатором.

Внутренняя реализация уже разделяет общую часть (slot pool, dispatcher,
orto_complete) — code share там где он естественный.

---

### 2.3. `await all { ... }` — два режима одного синтаксиса

**Что**:

```orto
let (a, b, c) = await all { e1, e2, e3 };  // статика → tuple
let arr = await all task_array;            // динамика → Array[Result]
```

Один `await all`, два разных типа результата, два разных лоwering'а.
Парсер выбирает по look-ahead на `{`.

**Проблема**: контекстная грамматика. Программист видит «await all» и
должен по аргументу понять, что вернётся.

**Решение: оставить как есть, но переименовать.**

Два режима оправданы — они решают разные задачи:
- Static: гетерогенный параллелизм. Прочесть размер файла и
  заголовки заявки одновременно — два разных типа.
- Dynamic: однородный fan-out. Запустить N одинаковых воркеров на
  список входов.

Оба нужны. **Но** название `await all` обеими формами читается чуть
двусмысленно. **Менять не буду** — `all` хороший компромисс. Делать
два разных слова (`await all` vs `await each`) — три кейворда вместо
двух, без выигрыша.

→ Записываю как «осознанное контекстное правило».

---

### 2.4. `yield` как отдельное слово

**Что**: `yield` — синтаксический ключевик. Семантически это `await`
на nop SQE.

**Проблема**: лишнее слово. По закону природы `yield` это
`await nop()`.

**Решение: оставить keyword.**

Альтернатива (stdlib `nop()`) требует чтобы каждая программа
использующая yield делала `use io::{nop}` или объявляла `extern fn
nop() -> Task[int]`. Это засоряет каждую async-программу импортом
для базовой кооперативной паузы.

Стоимость keyword'a: ~5 строк в парсере + 1 узел AST. Это меньше
чем dependency на builtin функцию. Сохраняем keyword.

---

### 2.5. `t.0` — числовое поле кортежа

**Что**: для кортежа `t` имеем `t.0`, `t.1`, ... — индекс, не имя.

**Проблема**: оператор `.` имеет два разных значения — field-by-name
(struct) и field-by-index (tuple).

**Решение: оставить как есть.**

Rust/Swift/Scala используют ту же нотацию. `t.0` интуитивно читается
как «нулевое поле кортежа». Альтернативы (`t[0]`, `fst(t)`) хуже:
- `t[0]` конфликтует с Array index, потребовалось бы развести по
  типу — добавляет контекстное правило.
- `fst(t)`/`snd(t)` не масштабируется на n>2.

Numeric field syntax — established practice, держим.

---

### 2.6. `extern fn ... -> Task[T]` vs `extern fn ... -> T`

**Решение: уже сделано (фаза 9).** Убрали модификаторы `async`/`stream`;
тип возврата сам определяет calling convention.

✅ Closed.

### 2.7. Three flavours of drop function

**Что**: три способа дропнуть линейное значение:

1. `drop_Region` — встроен в runtime.
2. `drop_<UserType>` — пишет пользователь.
3. `drop_Array_<T>` / `drop_Tuple_<T0_T1>` / `drop_Task_<T>` /
   `drop_Stream_<T>` — генерируется компилятором per instantiation.

**Решение: оставить как есть.**

Они **разные по природе** и это правильно отражено разными
механизмами:
- (1) Region — встроенный примитив рантайма, не выражается в orto.
- (2) User linear — resource ownership с пользовательской семантикой
  (close fd, free conn pool, etc.) — должен писаться пользователем.
- (3) Induced — структурный обход. Компилятор имеет полную
  информацию о структуре, генерация автоматическая.

Унификация (через vtable, например) добавила бы runtime cost (vtable
dispatch) ради косметической однородности. Не делаем.

### 2.8. `long long` ограничение на `Task[T]`

**Решение: уже сделано (фаза 10).** Расширил slot.result /
last_res / return_value до `uint8_t[16]`. Task[Array[byte]] и Task с
3-4-tuple теперь работают.

✅ Closed.

---

### 2.9. `for i in lo..hi` vs `for x in stream`

**Что**: один `for` keyword, две семантики, парсер дизамбигирует по
`..`.

**Решение: оставить как есть.**

Range form (`for i in lo..hi`) и iterator form (`for x in iterable`)
— стандартная двойственность в Rust/Python/Go/Swift. Парсер
определяет по synthetic token `..`. Программист видит `..` →
понимает что это range; видит обычное выражение → понимает что это
итерация. Это **локально читаемое** различие.

Альтернатива (`for i = lo to hi`) добавляет третий keyword за
маргинальное приобретение. Держим.

---

### 2.10. `await all` reserves `all` как контекстное слово

**Что**: `all` — обычный идентификатор кроме как сразу после `await`.

**Решение: оставить как есть.**

Эта контекстная грамматика **строго локализована**: `all` после
`await` встречается ровно в одной позиции AST. В любом другом месте
программы `all` — обычное имя. Парсер делает one-token-lookahead и
никуда дальше не идёт.

Один контекстный кейворд в одной позиции — допустимый налог за
естественность `await all`.

---

### 2.11. Frame-binder `fr->` префикс — implementation detail

**Что**: внутри `async_rewrite_to_frame` мы переименовываем имена
переменных, добавляя `fr->` префикс. Это видно в `emit.ml` и
определяет emission shape.

**Проблема**: implementation хак. Detection через string-prefix
matching.

**Решение: оставить как есть для V1.**

Эта вещь **не выходит на поверхность языка** — пользователь её не
видит. Это локальный хак в emit, ~5 мест touch его (`store_at`,
`frame_lvalue`, async_rewrite). Введение явного AST-узла
(`TEFrameVar`/`TEFrameLet`) потребовало бы пробрасывания через все
AST-проходы (resolve, check, mono, zonk, consume, emit) — порядка
50+ мест ради косметики во внутреннем эмиттере.

Цена > польза. Документировано в коде. Закрыто.

---

### 2.12. spawn-only-on-call ограничение

**Что**: `spawn worker(args)` — допустимо только когда внутри вызов
функции. `spawn 42` — отвергается с понятным сообщением.

**Решение: оставить — это семантическая необходимость.**

spawn семантически требует функцию и аргументы — без вызова нет
работы для запуска. Программа с `spawn 42` буквально лишена смысла.
Это не правило, это constraint конструкции. Закрыто.

## 3. Чек по N+M, не N²

Сколько мест компилятора задело Stage 3:
- `token.ml` / `lexer.ml` — 3 keyword'а (`await`/`spawn`/`yield`).
  (`async`/`stream` ушли в фазе 9.)
- `ast.ml` — 5 новых узлов async + 3 узла tuples.
- `parser.ml` — соответствующая парсинговая логика.
- `check.ml` — типизация (Task, Stream, Result, tuples, induced
  linearity propagation).
- `mono.ml` — пробрасывание новых типов.
- `emit.ml` — state machine, slot pool, runtime header, drop
  generators.

Это **много** — около 1500 LOC OCaml. Но это **одна ось** —
конкурентность. Если бы мы добавляли её несколько раз с разных углов
(один pass на await, другой на spawn, третий на Stream), было бы N².

По факту мы делали последовательно: каждая фаза опиралась на
предыдущую, **не модифицируя**. spawn использовал slot pool, который
тоже использовал await. Tuples использовали induced linearity которая
уже работала. И т.д.

Это **N+M**. Дорого, но честно.
